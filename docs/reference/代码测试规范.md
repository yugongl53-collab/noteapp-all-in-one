# 代码测试规范

## 1. 用途与适用范围

本文档规定一站笔记 Android 工程的代码测试方法和交付门禁，供功能开发、缺陷修复、重构、数据迁移和发布验收使用。目标是让业务规则能够稳定复现、失败路径不会产生错误成功状态，并让每次提交都有与风险相称的验证证据。

当前仓库已经建立 Android 工程，并完成 M0 至 M2。本文列出的 Gradle 命令均为当前工程的真实门禁；其中设备仪器测试必须连接 API 31 或更高版本的模拟器或实体手机。

产品是否正确由[产品需求文档](../product/产品需求文档.md)、[页面与交互说明](../product/页面与交互说明.md)和[数据模型与统计口径](数据模型与统计口径.md)共同定义；测试不能自行发明业务规则。

## 2. 测试工作流

每项代码变更按以下顺序执行：

1. 从需求或缺陷中列出正常、边界、无效输入和失败恢复场景，明确每个场景的输入、动作和可观察结果。
2. 选择能够验证该行为的最低测试层级。纯计算不启动 Android 环境，只有依赖 Android 框架或跨组件协作时才提升到集成测试、Compose 测试或仪器测试。
3. 新功能先写核心规则测试再实现；缺陷修复必须先增加一个可稳定失败的回归用例，确认失败原因与缺陷一致后再修改生产代码。
4. 先运行受影响的最小测试集，修复至通过；再运行所属模块测试、Lint 和当前阶段规定的完整门禁。
5. 记录执行命令与结果。不能执行的设备测试或发布测试必须说明原因、影响和后续验证条件，不能省略后宣称全部通过。

重构不改变可观察行为，但仍须运行原有测试；如果被重构代码没有足够保护，应先补充刻画当前正确行为的测试。只改文档时无需运行代码测试，但必须完成仓库规定的文档一致性检查。

## 3. 测试分层与放置

| 层级 | 适用内容 | 典型位置 | 主要约束 |
| --- | --- | --- | --- |
| 本地单元测试 | 日期展开、排序、重叠、随机候选过滤、计时状态机、统计和备份校验等纯 Kotlin 规则 | `app/src/test/` | 快速、无设备、不得依赖 Android 运行时或外网 |
| Room 集成测试 | DAO、唯一性和引用约束、事务回滚、数据库迁移、整体导入替换 | 工程建立后按实际运行环境放入 `app/src/test/` 或 `app/src/androidTest/` | 使用隔离数据库；每个用例自行准备和清理数据 |
| Compose 页面测试 | 表单校验、加载和空状态、错误反馈、导航与关键可访问语义 | `app/src/androidTest/` | 按用户可见结果断言，避免绑定内部组件结构 |
| Android 仪器测试 | 文件选择器适配、权限状态、系统调度、数据库与页面集成 | `app/src/androidTest/` | 明确 API 级别、授权前提和设备状态 |
| 实体手机人工验收 | 通知、准点提醒、后台运行、进程或设备重启、时区和省电策略 | Pull Request 或发布验收记录 | 记录设备、Android 版本、步骤和结果，不替代可自动化规则测试 |

一个场景只在能发现独立风险的层级重复。领域计算由本地单元测试穷举边界，页面测试只确认页面正确调用并展示结果；不能用大量缓慢的端到端测试代替精确的规则测试，也不能用纯 Kotlin 测试证明 Android 系统行为正确。

## 4. 用例设计规范

每个测试只表达一个可识别的失败原因，名称应描述“给定条件、执行动作、预期结果”，不使用 `test1`、`works` 等无业务含义的名称。测试代码沿用生产代码的注释要求，但清晰的准备、执行、断言结构无需逐行注释；只有复杂数据构造、业务边界或系统适配需要一句说明原因。

用例至少覆盖与本次变更相关的以下类别：

- 正常路径：有效输入产生规定结果并正确持久化或展示。
- 边界条件：最小值、最大值、空集合、首尾相接、日期首尾、跨午夜、跨时区和夏令时等适用边界。
- 无效输入：字段缺失、范围错误、重叠、悬空引用、未知格式版本和权限拒绝均被明确拒绝。
- 失败恢复：数据库、文件或系统接口失败时不产生部分写入，用户输入和可恢复状态符合产品约定。
- 状态变化：编辑、删除、重启、时区变化或权限撤销后，旧状态不会继续影响结果。

发布关键路径的最低场景如下：

| 领域 | 必测风险 |
| --- | --- |
| 日期与课程展开 | 学期第 1 周、首尾日期、有效周次闭区间、寒暑假、跨时区和夏令时 |
| 时间记录 | 无效时间范围、首尾相接允许、任意重叠拒绝、编辑排除自身、跨午夜切分 |
| 随机候选 | 只包含启用项目、空集合、单一候选、注入固定随机源后的确定结果 |
| 提醒调度 | 默认和自定义提前量、关闭、修改或删除后取消、错过提醒窗口、重启与时区变化 |
| 番茄钟 | 暂停与继续、绝对截止时间、进程恢复、阶段结束、过期提醒不补发 |
| 统计 | 五类聚合、稳定排序、同名合并、删除后重算、23/24/25 小时自然日与“其他” |
| 备份导入 | 完整往返、未知版本、字段错误、悬空引用、重叠记录、事务回滚和导入后提醒重建 |
| Room 迁移 | 每个已发布 Schema 到当前 Schema 的迁移、数据保留、约束与默认值 |

## 5. 可重复性与测试隔离

- 时间相关代码必须允许注入时钟和时区；测试使用固定时间点，不直接读取执行当下的系统时间。
- 随机选择必须允许注入随机源；集合正确性与固定输入结果需要确定性断言，公平性只做合理的大样本检查，不要求短样本严格平均。
- 异步测试等待可观察状态或测试调度器推进，不能用任意 `sleep` 猜测完成时机。
- 测试不得依赖执行顺序、外网、开发者个人目录、已有数据库、固定 AVD 名称或其他测试遗留数据。
- 文件和数据库测试使用每个用例独立的临时资源，并在结束后释放；测试失败也不得污染下一次执行。
- 不稳定测试视为缺陷。应修正时序、状态泄漏或环境前提，不得靠无限重试、扩大超时、降低断言或长期忽略测试掩盖失败。

若为实现上述可控性需要新增测试依赖，必须先说明它能够减少哪些测试代码、设备依赖或维护工作以及简化程度，并取得用户同意；不得擅自引入依赖，也不得为了绕过请示手写复杂替代框架。

## 6. 断言与测试替身

断言优先检查用户或调用方可观察的结果，包括返回值、持久化数据、公开状态、调度请求和页面语义。除非内部调用顺序就是接口契约，否则不要断言私有实现细节，以免安全重构导致无意义失败。

只替换测试范围之外的边界，例如时钟、随机源、文件接口或 Android 系统适配器；领域规则本身不得被模拟。替身返回值应在测试中明确，不共享会跨用例泄漏的全局可变状态。失败场景必须断言错误类型或状态以及数据未被部分修改，不能只断言“抛出了某个异常”。

## 7. 覆盖率与质量判断

覆盖率用于发现未执行的分支，不作为测试完成的唯一标准。当前工程尚未配置覆盖率插件或数值门槛；后续若引入，应记录统计命令、统计范围、排除项与初始门槛，降低门槛或扩大排除范围必须说明理由并经审查。

无论覆盖率数值如何，发布关键路径表中的适用场景都必须有可追溯用例。禁止为了提高数字编写没有有效断言的测试，也禁止通过排除难测业务代码制造达标结果。

## 8. 执行门禁与结果记录

当前 Android 工程使用以下真实命令；前三条不需要设备，`connectedDebugAndroidTest` 必须连接 API 31 或更高版本的模拟器或实体手机：

```bash
./gradlew testDebugUnitTest
./gradlew test
./gradlew lint
./gradlew assembleDebugAndroidTest
./gradlew connectedDebugAndroidTest
./gradlew assembleDebug
```

日常提交至少运行受影响的测试、所属模块测试和 Lint；涉及 Android 集成时增加仪器测试，涉及发布时按[MVP 执行计划与验证指南](../how-to/MVP实施与验证指南.md)执行完整构建和实体手机验收。测试失败时保留首个有意义的失败信息，先判断是生产缺陷、测试缺陷还是环境阻断，修复原因后重新运行相关门禁。

提交或 Pull Request 的验证记录至少包含：

- 实际执行的命令和通过、失败数量或明确的成功结果。
- 仪器测试使用的 API 级别；真机验收还要记录设备类型、Android 版本和关键步骤。
- 未执行的测试、阻断原因、风险范围和完成验证所需条件。
- 新增或修改的测试文件，以及它们对应的业务规则或回归缺陷。

不得使用“应该通过”“理论可行”代替实际结果。只有相关自动化门禁通过、必要真机场景已验证、文档与真实命令一致时，才能宣称该范围验证完成。

## 9. 提交前检查清单

- [ ] 需求或缺陷已转换为正常、边界、无效输入和失败恢复用例。
- [ ] 新增规则有测试，缺陷修复有先失败后通过的回归用例。
- [ ] 测试放在能发现风险的最低层级，没有重复验证私有实现。
- [ ] 时钟、时区、随机源、异步执行和测试数据可控且相互隔离。
- [ ] 受影响测试、所属模块回归和适用的 Android 门禁均已运行。
- [ ] 没有删除测试、弱化断言、忽略失败或用重试掩盖不稳定性。
- [ ] 验证命令、结果、未执行项和设备信息已如实记录。
- [ ] 用户可见行为、接口、命令或数据格式变化已同步相关中文文档。
